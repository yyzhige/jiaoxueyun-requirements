# 本轮升级摘要

## 核心变化

1. 原 PRD 从 27 个功能条目重构为 19 个模块级评审单元。
2. 将“长期 SaaS 愿景”与“石家庄公办初中试点”从目录、状态和就绪层面分开。
3. P0 主闭环拆为学校入口、教师工作台、作业创建、学生提交、AI 复核、成绩发布、成绩册、学生管理、掌握证据、提升计划、学生首页、订正、组织导入、AI 指令中心、权限审计。
4. 备课授课、综合考试成绩、辅助排课和管理员 CLI 被保留为长期合同，不再混入首轮试点承诺。
5. 每个模块新增页面入口、业务对象、owner 边界、字段、状态、权限、异常、验收、评估和开放决策。
6. 建立 Node ID、Prototype ID、Requirement ID 和 Acceptance ID 的追踪关系。
7. 当前包明确为产品评审输入；本轮不讨论技术仓库、接口、数据模型或开发排期。
8. 新增数据 Owner 中央矩阵，区分最终责任、日常维护、数据产生和正式确认。
9. 新增字段与选项字典，覆盖 19 个模块的下拉、单选、多选、级联、自动完成、默认值、联动、权限和失效规则。
10. 19 份模块 PRD 均回填 Data ID 与 Field ID 引用，派生视图明确继承源对象 Owner。
11. 新增跨模块 Data Flow Catalog，登记 21 条 Flow，覆盖输入输出版本、责任交接、可见性、幂等、部分失败、补偿和验收。
12. 19 份模块 PRD 均回填 Flow ID；成绩修正、证据修正、任课变更和上下文切换新增统一失效矩阵。

## 第一性原理修正

原 PRD 的主要问题不是方向错误，而是评审单元过大：一个功能 ID 同时覆盖多个页面、状态和角色，研发必须自行补齐关键产品判断。新版以“一个主要任务或稳定页面容器”为最小单元，跨模块只传递上下文，不复制规则。

本轮继续从第一性原理修正两个根因：数据必须有能够承担业务判断责任的人类 Owner；用户不能自由输入的字段必须有稳定选项合同。Owner 按权威业务对象定义，字段默认继承对象 Owner；Option Set 在中央事实源定义，模块 PRD 只引用，不重复创造枚举。

数据流转继续遵循同一原则：Flow 不是页面跳转，而是明确源 Data ID / 版本经过业务门禁产生目标 Data ID / 版本。权威写入成功后才能扇出，下游失败独立重试，上游变化使旧依据失效但不静默覆盖历史人工决定。

## 原型处理

旧 HTML 原型计划不再作为执行计划。产品确认后，应按模块 Prototype ID 选择高保真场景，而不是一次生成一个包含全部导航的静态大页面。
