# 第一性原理需求治理准则

本文件记录本项目在 v1.0 审查中暴露的缺陷，以及后续写需求时必须采用的行动准则。规则只保留能防止具体错误决策的内容。

## 1. 第一性原理

- 教学 SaaS 的核心事实不是页面，而是学校、身份、学生、作业、成绩、证据、计划、报告这些对象的责任和流转。
- AI 只能减少重复劳动和生成候选，不能绕过教师确认、学校治理和审计。
- 端不是角色，角色也不是权限；权限来自学校、学期、工作身份、职责、数据范围、业务动作和字段规则。
- 学生学习提升必须可执行、可跟踪、可再验证，否则只是解释文本。

## 2. 工作缺陷对应行动准则

| 曾暴露缺陷 | 正确行动准则 | 防止的错误决策 |
| --- | --- | --- |
| 先写页面，后补对象 | 任何模块先定义 Data ID、Owner、状态、Field、Flow，再写页面 | 页面看似完整但研发无法判断数据来源和责任 |
| 把角色和端绑定 | Web/App 只是能力承载位置，所有角色均可登录两端 | 学生只能 App、教师只能 Web 导致权限模型错误 |
| 把班主任当成全能教师 | 班主任拥有本班全科查看与协调，不拥有他科专业写权 | 班主任误改他科学科评分和计划 |
| 把 AI 输出当事实 | AI 输出先是建议、草稿或候选；正式事实由有权角色确认 | 未经教师确认向学生发布结论 |
| 字段没有下拉来源 | 每个选择型字段必须绑定 Option Set、来源、默认、失效规则 | 前后端各自造枚举，历史数据失真 |
| 数据没有 Owner | 每个 Data ID 必须声明主体、产生者、业务 Owner、确认者、Steward、控制主体 | 出错后无人能纠正业务含义 |
| Flow 没有补偿 | 每个跨模块 Flow 必须写源版本、目标版本、幂等、失败、补偿、下游失效 | 部分成功后状态无法恢复 |
| 把终端命令行当产品能力 | 一句话操作限定在 Web/App 内，必须可视化预览和确认 | 产品形态偏离教师学生使用画像 |
| P0/P1 当成颗粒度差异 | 优先级只表示交付顺序，所有模块文档完整度一致 | 低优先级模块留下语义空洞 |
| 第二阶段扩展混入第一阶段 | 第三方通知、AI 视频只登记边界，不展开第一阶段需求 | 范围失控影响主闭环验证 |

## 3. 每次改需求包的检查顺序

1. 先确认产品目标和不可变决策是否被改变。
2. 再确认 Data ID、Owner、Field、Option Set、State、Flow 是否完整。
3. 再看 Web/App Capability Matrix 是否明确差异。
4. 最后写页面、验收和交接说明。
5. 改完后扫描无 Owner、无 Option Set、无 Flow、无验收、终端命令行正向需求和开放决策阻断项。
