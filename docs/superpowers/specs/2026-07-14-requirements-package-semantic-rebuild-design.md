# 知序教学云需求包语义重构设计

| 属性 | 值 |
| --- | --- |
| 日期 | 2026-07-14 |
| 适用基线 | 知序教学云产品总基线 v2.0 |
| 目标仓库 | jiaoxueyun-requirements |
| 变更性质 | 需求生成模型与 v2.0 需求包全量重构 |

## 1. 问题与目标

现有 v2.0 需求包完成了文件、编号和中央目录建设，但生成器以统一模块模板为中心，造成结构完整而业务语义不足。此次重构必须解决以下问题：

- 模块功能需求、页面合同和权限不再由通用模板直接复制。
- 每个权威对象必须有完整字段、关系、状态、Owner、生命周期和版本规则。
- 每个业务动作必须能追溯到操作者、权限、输入、状态变化、Flow、页面动作和验收场景。
- AI 对话只能调用已登记任务，不能凭自然语言绕过模块动作合同。
- 机械扫描必须验证语义引用关系，不能只统计 ID 是否存在。

完成标准不是重新生成 27 份文件，而是主闭环可以由产品、设计、研发和 QA 使用同一组事实独立完成原型、接口设计和测试拆分。

## 2. 方案选择

### 方案 A：在现有文档上逐项修补

优点是变更量小。缺点是模板根因仍在，重新运行生成器会覆盖人工修复，中央合同与模块文档继续漂移。

### 方案 B：只重构 P0 主闭环

优点是较快进入核心原型。缺点是 P1-P3 继续使用旧语义模型，中央 Owner、权限和 Flow 无法保持全局一致，也不符合“优先级只表示交付顺序”的既定规则。

### 方案 C：重构生成模型并全量再生

该方案先建立对象、动作、状态、权限、Flow、场景和页面的结构化事实，再由生成器输出 27 个模块。工作量最大，但能消除模板根因并保持全包一致性。

决策：采用方案 C。P0-P3 文档完整度一致，优先级只控制实现顺序。

## 3. 事实分层

### 3.1 产品基线

产品基线只保存目标市场、试点边界、产品端、角色原则、主闭环、成功指标和阶段边界。模块文档不得反向修改基线。

### 3.2 领域事实

生成模型必须保存以下中央事实：

- 角色与职责：登录角色、可挂载职责、职责授权者和有效范围。
- 权威对象：对象 ID、业务 Owner、数据主体、控制主体、Steward、敏感级别和生命周期类型。
- 对象字段：业务字段、数据类型、必填条件、默认规则、值来源、可变性、可见性、校验和历史策略。
- 对象关系：源对象、目标对象、关系类型、基数、归属范围和删除或失效行为。
- 状态机：对象、起始状态、目标状态、触发动作、操作者、前置条件、阻断条件、副作用和补偿。
- 动作合同：动作 ID、目标对象、输入、输出、权限表达式、风险等级、幂等规则和审计要求。
- Flow 合同：参与动作、源 Data ID 与版本、目标 Data ID 与版本、扇出对象、失败粒度、重试、补偿和下游失效。
- AI 任务：自然语言能力只能映射到已登记动作或只读查询。
- 观测指标：指标口径、事件、起止点、聚合方式、Owner 和试点目标。

### 3.3 模块交付事实

模块 PRD、页面合同、追踪矩阵和角色交接材料只能由领域事实派生。模块可以补充业务叙述，但不能重新定义中央对象、状态、权限或 Flow。

## 4. 模块 PRD 结构

每个模块必须包含以下内容，不能用固定数量的通用 FR 代替：

1. 模块目标、用户问题、进入条件和退出条件。
2. 本模块拥有和引用的权威对象及关系。
3. 按对象拆分的完整字段合同。
4. 按对象拆分的状态转移表。
5. 按业务动作拆分的功能需求，每个动作独立编号。
6. 角色、职责、数据范围、动作和字段级权限。
7. 主流程、异常流程、并发冲突、幂等和补偿。
8. Web 与 App 的任务级承载差异。
9. 场景式验收标准和非功能验收。
10. 基线决策、Data ID、Action ID、Flow ID、Page ID、Metric ID 和 Test Scenario 的追踪关系。

功能需求数量由业务动作决定。登录、作业发布、AI 批改和长期路径不要求相同数量，也不共享无业务意义的功能名称。

## 5. 核心闭环深化规则

### 5.1 作业创建与发布

至少覆盖作业基本信息、适用范围、开放时间、截止时间、迟交策略、重提策略、题目内容、答案、分值、Rubric、知识点、反馈开放、发布版本和撤回或修订规则。

### 5.2 学生作答与提交

至少覆盖文本答案、选择答案、附件、图片页、题目映射、上传质检、草稿版本、离线与弱网恢复、漏答提示、迟交、重提和提交回执。

### 5.3 AI 初评与教师复核

必须建立“学科、题型、提交方式、识别能力、评分能力、置信门槛、强制复核、批量确认”能力矩阵。评分建议必须包含题目、提交版本、Rubric 版本、建议得分、评分依据、置信状态和限制说明。正式评分只能由对应任课职责确认。

### 5.4 成绩、证据与提升计划

成绩修正必须使依赖旧版本的证据、掌握判断、提升候选和报告解释进入失效或待确认。提升计划必须定义目标、任务内容、工作量、截止时间、成功条件、执行证据、困难反馈、再验证方式和关闭原因。

### 5.5 报告与长期路径

报告订阅和报告运行必须是不同对象和状态机。长期路径跨学期保存事实引用；历史事实不可改写，但新的教师确认解释可以形成新版本并注明适用时间。

## 6. 权限模型

权限判断仍遵循“学校、学期、工作身份、职责授权、数据范围、业务动作、字段规则”，但输出矩阵改为动作级合同。

- 学生只执行本人学习动作和查看已开放内容。
- 任课教师只对本人任教学科和班级执行专业写操作。
- 班主任拥有本班全学科查看和协调动作，不获得他科评分、掌握判断和学科计划写权。
- 教务管理组织、课程、考试、排课和授权汇总，不默认获得专业判断写权。
- 学校管理员管理账号、策略、治理和审计，不默认浏览学生学习明细。
- 平台运营只执行学校入驻和服务治理动作，默认不能访问学生明细。
- 学科负责人定义为教师工作身份上的可授权职责，不新增独立登录角色。

无业务动作的角色不生成允许权限行。禁止把一套角色描述复制到所有模块。

## 7. AI 对话任务模型

AI 任务注册表至少包含：任务 ID、面向角色、支持端、自然语言示例、目标 Action ID、参数结构、缺参澄清、风险等级、是否写入、预览字段、确认者、结果结构、失败处理和可撤销性。

任务分为查询、分析、临时报表、草稿、受控执行和定期任务。查询和分析不得写入业务事实；草稿必须由有权角色确认；受控执行只能调用目标模块 Action；定期任务只管理报告订阅和学校批准的周期动作。

学生 AI 必须遵守答案、解析、成绩和反馈开放策略。AI 不可用时，作业提交、教师批改、成绩发布和计划维护保留人工路径。

## 8. Web 与 App 页面合同

页面由用户任务生成，不再固定为列表、详情、确认和审计四页。

- Web 承载复杂编辑、批量处理、完整数据对比、配置和审计。
- App 承载学生学习主流程、教师高频查看与低风险确认、班主任移动协调和通知处理。
- 所有角色可以登录两端，但每项能力必须明确 Web、App、两端或不适用。
- App 被省略的能力提供明确去向，不暗示用户失去权限。

页面合同必须引用 Action ID 和 Field ID，验收场景必须引用 Page ID。第二阶段模块只登记入口、依赖和边界，不生成可执行页面动作。

## 9. 验收与非功能要求

每个业务动作至少包含一个成功场景和一个失败或边界场景，格式统一为前置条件、触发动作、预期数据、预期状态、权限结果和可见结果。

第一阶段必须补充以下可量化要求：

- 试点规模和峰值提交、上传、批改、报告任务容量。
- Web/App 支持范围、弱网和离线恢复边界。
- 图片大小、数量、格式、上传重试和失败保留规则。
- 关键查询、保存、批量操作和 AI 异步任务的响应目标。
- 权限拒绝、版本冲突、审计失败和 AI 不可用的降级行为。
- 未成年人学习材料、导出文件、AI 输入输出和审计数据的保留与访问规则。
- 产品成功指标对应的 Metric ID、事件和统计口径。

## 10. 生成器重构

生成器改为“事实定义、验证器、渲染器”三层：

- 事实定义层只保存结构化领域事实，不拼接 Markdown。
- 验证器在写文件前拒绝无 Owner、孤立角色、缺失字段、非法状态跳转、无权限动作、Flow 参与方不一致、无验收动作和阶段越界。
- 渲染器只负责从已验证事实生成中央合同、模块 PRD、页面合同和追踪矩阵。

生成器不得用默认字段、默认权限、默认功能需求或默认页面填满模块。缺失事实必须导致生成失败并指出模块与缺失项。

## 11. 一致性门禁

全量再生后必须通过以下检查：

1. 每个模块引用的 Flow 都包含该模块，反向参与关系也一致。
2. 每个 Action 的输入字段、目标对象和状态跳转都存在。
3. 每个选择型字段都有 Option Set；每个必需业务字段都进入对象字段合同。
4. 每个写 Action 有权限表达式、幂等规则、审计要求和失败结果。
5. 每个 AI 写任务映射唯一 Action，且有预览和确认者。
6. 每个 Page Action 映射 Action ID，每个 Action 至少有验收场景。
7. 每个基线成功指标映射 Metric ID 和采集事件。
8. 平台运营和学科负责人职责没有孤立 Owner。
9. 第二阶段模块没有第一阶段可执行页面或正向验收。
10. 不存在通用模板占位、无业务语义的重复 FR 或虚假通过报告。

## 12. 迁移与交付顺序

1. 保留产品基线 v2.0，先将当前需求包评审状态改为“语义审查未通过”。
2. 重构生成器数据结构和验证器，不直接手改生成产物。
3. 先录入组织、身份、作业、提交、批改、发布、成绩、证据、提升、AI、报告和长期路径事实。
4. 补齐其余 P0-P3 模块，使所有优先级达到同一文档完整度。
5. 全量再生中央合同、27 个 PRD、页面合同、追踪矩阵和交接说明。
6. 执行结构扫描、语义引用扫描和人工主闭环复核。
7. 只有全部门禁通过后，需求包状态才能恢复为原型与研发事实源。

## 13. 非范围

- 本次不设计前后端技术架构、数据库表或 API。
- 本次不生成最终视觉稿或 HTML 原型。
- 第三方通知、家长外部渠道、AI 讲题视频和 AI 教学视频只登记第二阶段依赖与边界。
- 不使用其他项目的需求上下文或 ForentX 需求资产。
