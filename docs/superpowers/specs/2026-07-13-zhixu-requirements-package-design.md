# 知序教学云需求交接包设计

## 1. 目标

把现有单体 PRD 从“产品方向说明”升级为可供产品、设计、前端、后端和 QA 分别审阅的模块级需求合同。交接包只定义产品可见行为与评审边界，不提前决定 API、DTO、数据库、组件库或仓库改动范围。

## 2. 第一性原理结论

研发能否正确实现，不取决于 PRD 的总字数，而取决于每个评审单元能否独立回答以下问题：

1. 谁从哪里进入，当前学校、身份、学期、班级和学科上下文是什么。
2. 页面或流程操作的业务对象是什么，哪些相邻能力不归本模块所有。
3. 用户可见字段、默认值、状态、权限、异常和返回刷新规则是什么。
4. AI 在哪里只能建议，哪里必须由教师或教务确认。
5. 什么证据可以证明需求被满足，什么条件仍阻止研发开工。

## 3. 采用方案

采用“模块族交接包”方案：一个总包管理索引与评审状态，每个页面级或任务级模块拥有独立 PRD、线框合同和模块评审清单。

未采用的方案：

- 继续扩写单体 PRD：阅读方便，但页面、状态和 owner 边界会继续互相覆盖。
- 直接开始高保真 HTML：可以快速看到界面，但会把未确认的产品判断固化进原型，返工成本最高。

## 4. 分层

| 层级 | 事实源 | 用途 |
|---|---|---|
| 产品基线 | `docs/product/zhixu-teaching-cloud-prd.md` | 保存产品愿景、试点目标和跨模块原则。 |
| 模块 PRD | `03-full-prd-md/` | 定义模块拥有的页面、对象、规则、字段、状态和验收。 |
| 线框合同 | `05-full-wireframe-md/` | 定义页面骨架、信息层级、交互载体和 Prototype ID。 |
| 结构化需求摘要 | `07-structured-requirements/` | 汇总模块范围、角色、字段、状态、验收和开放问题，方便检索。 |
| 角色交付说明 | `08-role-handoffs/` | 分流产品、设计、前端、后端和 QA 的关注点。 |
| 模块评审清单 | `09-review-checklists/` | 检查字段、状态、权限、异常、验收和开放问题是否完整。 |

## 5. 模块拆分原则

- 一个模块只拥有一个主要用户任务或一个稳定页面容器。
- 列表、详情、创建、复核、发布等载体在交互和状态明显不同时分开。
- 跨模块只声明入口、上下文和刷新合同，不复制下游模块规则。
- P0 试点模块写到产品评审颗粒度；P1-P3 模块保留完整边界和开放决策，但不得标记为可研发。

## 6. 就绪语义

| 状态 | 含义 |
|---|---|
| `产品评审稿` | 产品规则已形成可审阅草稿，仍需人工确认。 |
| `概念边界稿` | 长期能力已有边界，但关键产品判断尚未收敛。 |
| `产品已确认` | 产品负责人已确认范围、规则和开放问题处理结论。 |
| `待技术方案` | 产品形态已确认，下一阶段再讨论技术方案。 |

本轮所有模块最多到 `产品评审稿`；HTML 产品原型等待产品确认，技术方案继续后置。

## 7. 自审门禁

- 模块 ID、Node ID、Prototype ID 和验收 ID 不重复。
- P0 主闭环从学校入口到提升计划能完整追踪。
- 任课教师与班主任权限不互相覆盖。
- 主观题、成绩发布、计划生效和排课发布均保留人工确认。
- 学生只能看到已发布内容；AI 和学校切换遵守上下文隔离。
- 文档不包含真实凭据、真实学生数据或未授权实现假设。
