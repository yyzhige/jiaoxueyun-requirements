# 知序需求包数据流转合同设计

## 1. 问题

现有需求包已经有对象关系、状态、Data Owner、上游输入和下游输出，但没有统一回答以下问题：

1. 什么业务动作触发数据流转。
2. 流转读取哪个 Data ID 和哪个版本。
3. 哪个角色执行、确认并接管下一阶段责任。
4. 生成哪些新对象、版本、派生视图、通知和审计记录。
5. 部分失败、重试、重复请求和上游修正时如何处理。

因此当前材料不能直接作为 Mock 接口、跨模块联调和端到端测试的完整产品合同。

## 2. 第一性原理

1. 数据流转不是“页面跳转”，而是权威业务对象从一个有效版本产生另一个对象或版本。
2. 每条流必须有唯一 Flow ID、明确触发条件、源版本、目标版本和完成条件。
3. 读取、生成、确认、发布和查看是不同动作，不能用一个“成功”状态代替。
4. AI、求解器和异步任务只能产生建议、草稿或过程结果；正式值仍由对应业务 Owner 确认。
5. 写入成功后才允许向下游扩散；部分成功必须按对象返回结果，不能把整个批次显示为完全成功。
6. 同一业务动作重复提交不得重复产生正式结果；产品合同必须定义业务幂等键。
7. 上游版本变化不得静默覆盖下游人工决定，而是使引用失效、触发重算候选或要求重新确认。
8. 派生视图可以延迟刷新，但必须显示数据时间和来源版本，不能成为第二份权威事实。

## 3. 方案选择

### 方案 A：在每份 PRD 独立描述流转

模块阅读直接，但同一发布、修正、权限刷新和审计规则会重复出现并产生冲突。

### 方案 B：只绘制端到端总流程图

容易理解主路径，但不能定义版本、失败、补偿、责任交接和验收。

### 方案 C：中央 Flow Catalog 加模块薄引用

中央文件定义完整 Flow Contract，模块 PRD 引用相关 Flow ID，只补模块内页面行为。采用方案 C。

## 4. Flow Contract 结构

每条流至少包含：

| 属性 | 含义 |
|---|---|
| Flow ID | 稳定跨模块编号 |
| 优先级 | P0、P1、P2、P3 |
| 触发者 / 触发条件 | 谁在什么前置状态下启动 |
| 输入 | Data ID、版本和必要范围 |
| 处理 | 产品业务规则与人工确认门禁 |
| 输出 | 新 Data ID、版本、派生刷新、通知和审计 |
| Owner 交接 | 流转前后最终责任与确认角色 |
| 可见性变化 | 哪些角色何时可以看到哪些字段 |
| 执行方式 | 即时、后台、人工确认或扇出刷新 |
| 幂等键 | 防止重复正式写入的业务唯一组合 |
| 失败 / 重试 | 整体失败、对象级失败和安全重试规则 |
| 失效 / 补偿 | 上游变化后哪些下游对象失效或需重新确认 |
| 验收标准 | 可以被 QA 直接验证的结果 |

## 5. 产品与技术边界

本轮定义业务流转语义，不确定 API 路径、数据库表、消息中间件、Topic、队列产品或网络协议。技术设计必须保持 Flow ID、Data ID、版本、幂等和失败语义一致，但可以选择同步接口、异步事件或任务系统实现。

## 6. 首轮覆盖

P0 必须覆盖学校与身份、组织导入、作业发布、学生提交、AI 初评、教师复核、成绩发布、成绩修正、订正、学情、提升计划、责任交接、AI / CLI 高风险动作和审计。

P1-P3 建立备课、考试、排课、调课和自动化授权的完整合同骨架，不虚构目标学校未确认的业务参数。

## 7. 完成标准

1. 19 个模块都至少引用一条 Flow ID。
2. 每条 P0 流都有输入 Data ID、输出 Data ID、Owner 交接、幂等、失败和验收。
3. 每个权威下游写入都能追溯到源版本。
4. 成绩修正、证据修正、任课变更和上下文切换都有明确失效矩阵。
5. 评审清单能够发现缺少 Flow ID、失败规则或版本传播的模块。
