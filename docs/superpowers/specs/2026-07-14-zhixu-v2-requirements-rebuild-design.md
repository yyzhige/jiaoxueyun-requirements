# 知序教学云 v2.0 产品基线与需求包整体重构设计

状态: 已完成产品方向确认，等待用户审阅后进入实施计划
日期: 2026-07-14
目标产物: `docs/product/` 下的新产品基线与 `docs/requirements/zhixu-handoff-v2.0/` 完整需求包
历史处理: `zhixu-handoff-v1.0` 保留为历史评审稿，不在原目录覆盖

## 1. 重构目标

本次不是修补 v1.0，而是重新建立可信产品基线，再由基线推导完整需求包。重构完成后，产品目标、模块边界、权威对象、责任、字段、状态、权限、数据流、页面和验收必须能够互相追溯，任何一层不得依赖研发或原型临时补充产品判断。

完成条件不是文件数量，而是全量扫描中不存在阻断级缺失、冲突或无归属业务对象。

## 2. 事实优先级

新基线按以下顺序处理事实冲突：

1. 本轮对话中用户明确确认的产品决策。
2. 历史总 PRD 中未与明确决策冲突的目标、范围、指标和业务原则。
3. v1.0 需求包中的内容仅作为候选材料，不自动继承。
4. 未经确认且会改变体验、责任或范围的内容进入开放决策，不由文档编写者自行补齐。

文档与文档冲突时，先回到产品目标和权威对象判断，不按“较新的文件”机械覆盖。

## 3. 产品不可变核心

### 3.1 产品目标

在不降低成绩可信度和教师控制权的前提下，减少教师从收作业到发布反馈的重复劳动，并把作业结果转化为学生可执行、可跟踪、可再验证的下一步学习任务。

### 3.2 市场与试点

- 目标市场: 河北省石家庄市公办初中
- 采购与学校数据治理主体: 学校
- 试点范围: 一所学校、七年级、三个班
- 学科范围: 全学科共享作业、提交、反馈、成绩和提升流程
- AI 边界: 不承诺所有学科、所有题型自动判分

### 3.3 第一阶段主闭环

```text
学校与组织基线
-> 作业创建与发布
-> 学生在线或拍照提交
-> AI 初评
-> 教师复核
-> 成绩与反馈发布
-> 学生订正
-> 学情证据与掌握判断
-> 个性化提升计划
-> 学生执行与困难反馈
-> 后续学习证据再验证
```

### 3.4 第一阶段成功指标

| 目标 | 指标 | 试点目标 |
|---|---|---|
| 降低重复劳动 | 一轮作业反馈闭环的教师中位有效操作时长 | 相比试点前下降至少 30% |
| 建立行动闭环 | 查看反馈后进入订正或提升任务的学生比例 | 至少 60% |
| 保持教师控制 | 未经教师确认发布的主观题成绩数量 | 0 |
| 保持数据安全 | 跨学校、跨班级、跨学生越权事件 | 0 |
| 保持人工兜底 | AI 不可用时完成提交、批改和发布 | 主流程可完成 |

## 4. 产品端与角色模型

### 4.1 产品端

产品只有两个客户端：

- Web: 全量业务工作台，承载全部角色的完整业务能力。
- App: 移动协作与学习端，承载高频、即时、现场和必要移动能力，不要求一比一复制 Web。

学生、教师、班主任、教务、学校管理员等角色均可进入 Web 和 App。端不是权限边界，角色也不与端绑定。

### 4.2 跨端原则

- 两端共享同一账号、学校、学期、工作身份、职责授权、状态和权威数据。
- Web 与 App 的差异必须登记在 Capability Matrix 中，不能由前端自行删减。
- Web 提供完整创建、批量处理、复杂表格、导入、排课和权限配置。
- App 优先提供待办、查看、提交、反馈、报告、提醒、审批和必要确认。
- 学生以 App 为主要学习端，但 Web 同样支持作业、反馈、订正、学习路径和 AI 对话。

### 4.3 教师统一工作身份

账号、工作身份、职责授权和数据范围分离：

- 同一教师在一个教师工作身份中可同时拥有任课教师、班主任等职责授权。
- 有效读取范围由当前有效职责分别授予后汇总。
- 写入权限按具体动作、业务对象和职责逐项校验。
- 班主任职责授予本班全学科查看与协调，不授予他科学科判断、评分和计划内容修改权。
- 教务、学校管理员、学生等不同工作身份不能通过职责汇总获得跨身份权限。

## 5. AI 对话与可视化任务执行

产品不建设终端 CLI。原“CLI”概念统一改为 Web/App 内的“一句话操作、快捷指令和 AI 对话任务执行”。

第一阶段 AI 能力分为：

1. 查询: 返回当前权限内的数据和来源范围。
2. 分析: 生成可解释结论、指标和限制说明。
3. 临时报表: 在当前会话中形成可下钻的即时视图。
4. 草稿: 生成作业、评语、计划、报告定义等业务草稿。
5. 受控执行: 通过结构化预览、重新校验、明确确认、幂等和审计执行既定任务。
6. 定期任务: 创建、修改、暂停和取消报告订阅等长期任务。

AI 不建立第二套业务事实。查询、报表、草稿和执行结果必须引用目标模块的 Data ID、源版本和权限结果。

## 6. 报表与长期学习路径

### 6.1 三种时间形态

| 形态 | 产品定义 | 保存规则 |
|---|---|---|
| 临时 | 当前对话或当前页面即时生成的查询与分析 | 会话内保留，可由用户另存为报表定义 |
| 定期 | 按日、周、月或自定义周期生成的报告快照 | 保存订阅定义、每次运行快照、数据时间和源版本 |
| 长期 | 跨学期、学科、知识点和学习活动持续形成的学习路径 | 保存事实引用、确认过的解释版本和变化时间线 |

### 6.2 定期报告

- 用户可通过 AI 对话创建订阅，例如每日生成班级学习画像。
- 创建前展示周期、时间范围、学生范围、学科范围、指标、接收角色和权限预览。
- 报告进入 Web/App 报告中心，站内通知只发送摘要和查看入口。
- 第一阶段不向微信、短信、邮件等第三方渠道发送学生明细。
- 任课教师订阅本学科，班主任订阅本班跨学科汇总，教务只订阅授权汇总。

### 6.3 长期学习路径

- 自动进入时间线的事实包括已发布成绩、作业完成、订正结果、计划执行和教师确认记录。
- 知识点归因、错误模式、能力趋势和下一步建议属于解释性结论。
- 解释性结论先形成候选，经对应任课教师确认后才进入学生可见路径。
- 班主任可查看本班跨学科路径摘要并协调负担，但不能代替学科教师确认专业结论。
- 长期路径是可追溯视图，不复制或改写源成绩、证据和计划事实。

## 10. 单模块完整标准

每个模块无论优先级，都必须包含：

- 目标用户、问题、价值和范围。
- Web/App Capability Matrix。
- 页面、入口、命令入口和权威对象。
- 完整字段 ID、类型、格式、校验、敏感级别、可见性、可变性和来源。
- Option Set 的稳定 code、来源、默认、权限、级联和历史规则。
- 状态、合法跳转、阻断条件和责任人。
- 角色、职责、数据范围和字段级权限。
- 主流程、异常、空状态、部分成功、幂等、重试和补偿。
- Data ID、Flow ID、源版本、目标版本和下游失效。
- 可测量验收 ID 和成功指标。
- 依赖、非范围、开放决策和就绪门禁。
- Web/App 线框及跨端差异。

不得使用“后续技术决定”掩盖产品语义，也不得因为模块优先级较低而降低需求颗粒度。

## 11. 数据与责任原则

责任至少分离为：

- 数据主体: 数据描述或关联的人。
- 产生者: 创建原始记录的人或系统。
- 业务 Owner: 对业务含义、正确性和纠正负责的角色。
- 确认者: 使候选或草稿成为正式业务值的人。
- 数据控制与治理主体: 学校。
- Steward/保管者: 负责日常质量、保留、归档和异常处理的角色。
- 技术处理者: 按授权处理数据的平台或第三方服务。

学生可以是本人作答的产生者和数据主体，但不承担学校系统中的数据控制、保留和删除责任。AI 只能是产生者或处理者，不能成为正式成绩、学情、计划或权限的业务 Owner。

## 12. 重构顺序

1. 建立并确认 v2.0 产品总基线。
2. 建立模块边界与跨端 Capability Matrix。
3. 建立权威对象、责任、课程知识点和数据生命周期合同。
4. 建立完整字段、Option Set 和状态机。
5. 建立 P0-P3 全量数据 Flow 和失败补偿合同。
6. 编写全部模块 PRD。
7. 编写全部 Web/App 线框合同。
8. 建立全量追踪矩阵。
9. 执行机械扫描与人工反证审查。
10. 仅在阻断项为 0 后标记为“可进入原型阶段”。

## 13. 全量扫描门禁

扫描必须验证：

- 基线中的每项能力至少被一个模块拥有。
- 每个权威对象有稳定 Data ID 和完整责任分配。
- 每个业务字段有 Field ID，选择字段引用有效 Option Set。
- 每个状态有稳定 code、合法跳转和对应责任人。
- 每个跨模块写入引用有效 Flow ID。
- 每个 Flow 有输入、输出、版本、权限、幂等、失败、补偿、审计和 Acceptance ID。
- 每个 Requirement ID 至少关联一个 Acceptance ID。
- 每个 P0-P3 模块均有 Web/App Capability Matrix 和线框合同。
- AI、报告和长期路径不建立第二份源业务事实。
- 第一阶段范围不引用第二阶段未定义能力作为前置依赖。
- 模块 PRD、中央合同、线框和追踪矩阵不存在同义不同码或同码不同义。

机械扫描通过后仍需按身份、数据责任、状态流转、跨端行为和隐私生命周期做人工反证审查。机械一致不等于产品正确。

## 14. 非目标

- 本轮不讨论 React Native、Web 框架、API、数据库、模型供应商和部署方案。
- 本轮不设计第三方消息渠道。
- 本轮不展开 AI 讲题视频和 AI 教学视频的交互、生成链路或商业模式。
- 本轮不以静态页面数量代替完整任务闭环。
- 本轮不直接覆盖或删除 v1.0 历史材料。

## 15. 设计自检结论

- 新设计已消除终端 CLI 与目标用户画像冲突。
- Web/App 与角色解耦，并明确 App 不要求完整复制 Web。
- 教师兼任职责使用统一工作身份，写权限仍按职责约束。
- 报表区分临时、定期和长期三种时间形态。
- 长期学习路径区分事实与解释性结论，并保留教师确认门禁。
- 知识点、通知、数据生命周期和审计均拥有独立权威边界。
- P0-P3 文档完整度一致，优先级只影响交付顺序。
- 第二阶段扩展没有成为第一阶段隐性依赖。
