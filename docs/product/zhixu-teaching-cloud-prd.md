## 0. 第一性原理审查结论

### 0.1 必须回答的核心问题

知序教学云的首要任务不是证明“可以生成很多教育页面”，也不是证明“AI 可以参与所有学校事务”，而是验证一个最小且完整的价值假设：

> 在不降低成绩可信度和教师控制权的前提下，系统能否减少教师从收作业到发布反馈的重复劳动，并把同一份作业转化为学生下一步可执行的学习任务。

### 0.2 试点必须证明的三件事

1. 教师完成“批改、复核、发布”的时间明显下降。
2. 学生能够从反馈进入订正和后续提升，而不是只看到分数。
3. 学校、班级、学科和身份边界不会因 AI 或角色切换发生越权。

### 0.3 试点不必证明的事项

- 不必在首轮证明所有学科、所有题型都能自动判分。
- 不必在首轮完成完整排课、商业运营、集团管理和私有化能力。
- 不必用 26 个独立页面证明产品完整性。
- 不必让 CLI 成为教师和学生的主要入口。
- 不必通过单一分数或排名证明学生能力。

### 0.4 审查后的产品边界

- “全科”表示全学科都能布置、提交、沉淀成绩和进入教师工作流。
- “AI 批改”按题型分级，自动判分不是所有学科的统一承诺。
- 长期产品愿景保持完整，试点只交付验证教学闭环所需的最小能力。
- 原型以关键任务贯通为目标，完整导航只用于表达未来产品结构。

## 1. 产品概述

### 1.1 背景

初中学校的作业、成绩、学生跟进和教学管理通常分散在纸质材料、表格、即时通讯工具和多个孤立系统中。教师需要重复完成批改、录分、统计和反馈，学生往往只能看到分数，难以理解错误原因及后续改进路径；班主任、任课教师与教务之间也缺少统一、可追溯的协同机制。

AI 能够辅助识别作业、生成评分建议、归纳知识薄弱点并形成学习计划，但其结论必须嵌入教师复核、权限控制、数据留痕和学校管理流程，不能替代教师的专业判断。

### 1.2 问题陈述

- 教师重复批改、录分和整理数据耗时较高。
- 学生收到的反馈停留在分数和答案，缺少错误原因与改进路径。
- 作业、成绩、知识点掌握和提升计划之间没有形成连续闭环。
- 任课教师只关注单学科，班主任缺少全学科任务和风险视角。
- 教务排课、班级、课程和成绩管理的数据关系分散。
- 自然语言 AI 工具与业务系统割裂，无法安全执行教学任务。

### 1.3 产品定义

知序教学云是一套面向公办初中的学校级教学 SaaS。产品以作业与成绩数据为入口，通过 AI 辅助批改、教师复核、学情诊断和个性化提升形成持续教学闭环，同时提供教师学生管理、学生学习、教务排课和学校组织能力。

产品包含：

- 教师端 Web
- 教务与学校管理端 Web
- 学生端 App
- 平台运营端 Web
- AI 指令中心与连续对话
- 面向管理员和集成方的 CLI 能力

### 1.4 产品原则

- AI 是教学辅助层，不替代教师最终判断。
- 学校是租户，身份是权限入口，两者不能混为一体。
- 学科教师负责专业内容，班主任负责全学科协调。
- 学生端以今日行动为核心，不以排名和游戏化为核心。
- 所有成绩、计划和 AI 操作均可追溯。
- 未成年人数据按最小必要原则展示和处理。
- 先形成完整产品结构，再分阶段开放复杂能力。

### 1.5 长期产品愿景范围

- 学校选择、账号、身份、学期和多租户管理
- 教师作业、AI 辅助批改、成绩、学生管理和学情分析
- 学生 App 的作业、订正、错题和个性化提升
- 班主任全科学情协调
- 教务组织、课程、考试、排课和教学数据
- AI 指令中心、连续对话、操作预览和审计
- 面向管理员与集成方的 CLI
- 受控家长学习报告分享
- 集团、区域和私有化扩展能力

### 1.6 试点范围

试点采用“一所学校、七年级、三个班”的范围，优先贯通以下能力：

- 学校选择、账号激活、身份选择和学期上下文
- 基础年级、班级、教师、学生和任课关系导入
- 全学科作业创建、在线答题和拍照提交
- 分级 AI 初评、教师复核、成绩发布和成绩版本
- 基础成绩册、逐题反馈、错题订正和知识点证据
- 基础个性化提升计划及任课教师、班主任同步
- 教师工作台、学生 App 首页和关键消息提醒
- AI 指令中心的查询、分析和草稿生成
- 权限校验与关键操作审计

试点不承诺全学科、全题型自动判分。语文、英语开放题和文科材料题以识别、评分点辅助和评语草稿为主，最终得分由教师确认。

### 1.7 试点外范围

- 完整考试综合成绩和复杂权重配置
- 完整学校题库和区域题库运营
- 辅助排课的正式生产发布
- 独立家长端或家长 App
- 学生之间的社交、私聊和公开社区
- 完整在线课程商城
- 平台商业运营和集团汇总分析
- CLI 的生产级交付
- 复杂走班、跨校区和区域统筹排课
- AI 自动作出分班、处分、升学或教师评价决定
- 本期技术架构、接口和部署方案

## 2. 目标与成功指标

### 2.1 业务目标

| 目标 | 指标 | 试点目标 |
|---|---|---|
| 降低教师重复劳动 | 从开始批改到完成发布的教师有效操作时长 | 相比试点前中位数下降 30% 以上 |
| 建立学习闭环 | 已查看反馈的学生进入订正或提升任务的比例 | 60% 以上 |
| 提升反馈质量 | 已发布作业包含可理解错误原因和下一步行动的比例 | 90% 以上 |
| 保持教师控制 | 未经教师确认发布的主观题成绩数量 | 0 |
| 提高学校可运营性 | 学校独立完成基础配置和成员导入 | 在标准指引下完成一次全流程 |

### 2.2 北极星指标与护栏

**北极星指标：教师完成一轮作业反馈闭环的中位有效操作时长。**

该指标从教师开始处理已提交作业起算，到成绩和反馈发布结束，排除系统后台等待时间。选择该指标是因为它同时反映识别质量、AI 分流、复核效率和发布流程是否真正减少教师劳动。

**护栏指标：**

- 未经教师确认发布的主观题成绩为 0。
- 跨学校、跨班级和跨学生的越权事件为 0。
- 学生因图片质检误判而无法提交的阻断率低于 2%。
- 教师可以在 AI 不可用时完成纯人工批改与发布。

### 2.3 用户目标

- 教师减少重复批改和整理工作，把时间用于教学判断和学生辅导。
- 学生知道错在哪里、为什么错以及下一步如何提升。
- 班主任掌握本班全科学习负担、重点问题和协同事项。
- 教务统一维护课程、班级、排课、考试与教学数据。
- 学校管理员可配置成员、权限、数据范围和 AI 使用边界。

### 2.4 核心 KPI

| 指标 | 定义 | 试点目标 | 测量方式 |
|---|---|---|---|
| 客观题高置信度接受率 | 高置信度客观题中教师未改分直接确认的比例 | 90% 以上 | 批改版本记录 |
| 过程题复核效率 | 数理过程题单题教师复核中位时长 | 相比纯人工下降 20% 以上 | 复核操作时长 |
| 开放题辅助采用率 | 教师采用 AI 提供的评分点命中或评语草稿的比例 | 60% 以上 | 教师编辑与采用记录 |
| 拍照提交可用率 | 无需学生重拍即可进入批改的提交比例 | 90% 以上 | 上传与识别状态 |
| 反馈到订正转化率 | 已查看反馈的学生中开始订正的比例 | 60% 以上 | 反馈与订正事件 |
| 错题订正完成率 | 已开始订正的错题中完成订正的比例 | 70% 以上 | 订正任务记录 |
| 提升任务完成率 | 到期前完成的个性化任务比例 | 60% 以上 | 学习计划记录 |
| 知识点再验证通过率 | 进入提升计划的知识点在后续同类题中达到教师设定通过条件的比例 | 建立基线，不作为首轮上线门槛 | 作业与测验证据 |
| 数据越权事件 | 跨学校、跨班级或跨学生的未授权访问 | 0 | 安全审计记录 |

## 3. 用户与权限

### 3.1 目标用户

| 用户 | 核心职责 | 主要终端 |
|---|---|---|
| 学生 | 完成学习、作业、订正和提升任务 | 学生 App |
| 任课教师 | 负责所教学科作业、成绩和学情 | 教师 Web |
| 班主任 | 查看并协调本班全科学情和任务 | 教师 Web |
| 教务人员 | 维护课程、教学任务、考试和排课 | 教务 Web |
| 学校管理员 | 维护学校组织、账号、权限和数据策略 | 管理 Web |
| 平台运营人员 | 学校入驻、平台内容和服务运营 | 平台 Web |

### 3.2 权限模型

可执行操作由以下四项共同决定：

```text
角色权限 × 当前学校 × 数据范围 × 当前身份
```

一个账号可以拥有多个身份，例如“数学教师 + 班主任 + 教务人员”。身份切换后，导航、数据范围和 AI 上下文必须同步切换。

### 3.3 权限规则

- 学生只能访问本人已发布的作业、成绩和学习计划。
- 任课教师管理所教班级和所教学科。
- 班主任查看本班全科情况，并协调跨学科任务总量。
- 班主任不能直接修改其他教师的学科题目或评分判断，除非同时拥有对应学科权限。
- 教务查看授权年级和学校范围的教学数据。
- 学校管理员拥有配置权，不默认拥有所有学生内容的浏览权。
- 平台运营人员默认只能访问运营状态和汇总信息。
- 技术支持访问学校明细需要学校授权、限时审批和完整审计。

## 5. 核心用户流程

### 5.1 主教学闭环

```text
教师创建作业
→ 学生在线答题或拍照提交
→ 系统识别与 AI 初评
→ 教师复核异常与主观题
→ 发布成绩和反馈
→ 学生完成订正
→ 系统更新知识点证据
→ 生成个性化提升计划
→ 后续作业或测验验证效果
```

### 5.2 学科协同流程

```text
系统发现某学科提升点
→ 同步对应任课教师
→ 任课教师确认或调整
→ 纳入学生总提升计划
→ 班主任检查全科负担和冲突
→ 学生执行
→ 结果同步任课教师与班主任
```

### 5.3 AI 指令执行流程

```text
用户输入自然语言指令
→ AI 识别意图与参数
→ 检查权限和数据范围
→ 缺失信息时追问
→ 生成查询结果或操作草稿
→ 展示影响范围和执行预览
→ 用户确认
→ 调用业务能力
→ 返回结果并记录审计
```

### 5.4 教务排课流程

```text
建立教学任务
→ 配置排课约束
→ 生成排课建议
→ 检查教师、班级和教室冲突
→ 教务人工调整
→ 发布课表
→ 调课、代课和变更留痕
```

### 6.1.1 试点题型覆盖矩阵

| 题型 | 学科示例 | AI 在试点中的职责 | 教师职责 |
|---|---|---|---|
| 标准客观题 | 全学科选择、判断、匹配 | 识别并自动判分，高置信度进入抽查 | 配置答案并抽查异常 |
| 受限填空题 | 单词、数值、术语、公式结果 | 按标准答案和允许变体给出判分建议 | 确认允许变体和最终结果 |
| 数理过程题 | 数学、物理、化学计算和证明 | 识别步骤、匹配评分点、建议分步得分 | 必须复核过程和最终得分 |
| 阅读与简答题 | 语文、英语、道法、历史等 | 提取要点、匹配评分点、生成评语草稿 | 必须确认评分点和得分 |
| 作文与开放题 | 语文作文、英语写作、开放材料题 | 辅助结构分析、问题提示和评语草稿 | 独立作出最终评价和得分 |
| 实践与非标准任务 | 实验、背诵、阅读、活动记录 | 整理提交材料和完成状态 | 按任务标准人工确认 |

全学科共用作业、提交、反馈、成绩和提升流程；自动化程度由题型与学校规则决定，而不是由“学科是否接入”决定。

### 6.2 TENANT-001 学校选择

**用户故事**

## 7. 关键业务规则

### 7.1 AI 操作安全等级

| 等级 | 示例 | 处理方式 |
|---|---|---|
| 查询 | 查询缺交学生、分析趋势 | 直接执行 |
| 草稿 | 生成作业、评语、计划 | 保存草稿 |
| 可逆修改 | 调整分组、修改计划 | 预览后确认 |
| 高风险操作 | 发布成绩、批量通知、调课、删除 | 二次确认与审计 |

### 7.2 排名

- 学生端默认不展示完整班级排名。
- 学生可查看本人分数段、趋势和知识点变化。
- 教师和教务按授权查看内部排名。
- 家长报告不展示其他学生姓名和成绩。
- 排名必须标明考试范围、参与人数和时间。

### 7.3 学生关注事件

系统使用可关闭的事件提醒，不形成永久标签。提醒类型包括连续缺交、多学科任务堆积、长期未改善、成绩波动、订正未通过、计划未完成和学生主动反馈困难。

### 7.4 通知

- 通知用于教学事务，不扩展为完整社交聊天。
- 支持学校公告、班级通知、个人提醒和系统消息。
- 学生 App 支持安静时段。
- 批量发送前显示接收范围、正文和时间。
- 第一版不提供学生之间私聊。

### 7.5 家长报告

- 学校可配置是否允许分享。
- 使用限时链接或一次性验证码。
- 只包含已发布内容和当前学生数据。
- 不包含教师私密备注、AI 内部判断和其他学生明细。

## 8. 状态模型

| 对象 | 状态 |
|---|---|
| 作业 | 草稿、待发布、进行中、已截止、批改中、待发布成绩、已完成 |
| 学生提交 | 未开始、进行中、上传中、已提交、需补充、已退回、已批改 |
| AI 批改 | 排队中、识别中、批改中、待复核、已确认、失败 |
| 成绩 | 未录入、待审核、已确认、已发布、已修正 |
| 提升计划 | 草稿、待确认、待开始、进行中、待评估、已完成、已调整 |
| 排课任务 | 草稿、计算中、存在冲突、待确认、已发布、已调整 |
| 批量导入 | 待上传、校验中、存在错误、待确认、导入中、部分成功、已完成 |

学生端不展示 OCR、模型超时、队列等内部术语。内部错误必须转换为用户可采取行动的提示。

## 9. 异常与空状态

### 9.1 学生提交异常

- 图片模糊：定位具体页并引导重拍。
- 页面缺失：展示要求页数和已上传页数。
- 上传中断：保留本地进度并支持继续。
- 重复提交：确认覆盖或追加。
- 超过截止：根据学校规则展示补交入口。

### 9.2 AI 批改异常

- 无法识别：转人工处理。
- 识别不完整：教师修正识别文本。
- 评分依据不足：不强行给分。
- 服务不可用：自动重试并保留人工批改入口。
- 结果异常：允许整份重新识别。

### 9.3 空状态

- 无作业：引导创建第一份作业。
- 无成绩：引导导入或完成批改。
- 无知识点结论：说明数据量不足。
- 无提升计划：说明生成条件。
- 无待办：展示今日课程和下一项建议。

## 10. 数据与隐私需求

### 10.1 核心数据关系

```text
学校 → 学期 → 年级 → 班级 → 课程
                       ↓
学生 → 作业提交 → 批改结果 → 成绩 → 知识点证据 → 学习计划
                       ↑
                 教师复核与调整
```

### 10.2 数据可见原则

- 学生仅查看本人已发布数据。
- 任课教师查看所教学科。
- 班主任查看本班全科。
- 教务按履职范围查看汇总和必要明细。
- 学校管理员负责配置和审计，不默认浏览全部教学内容。
- 平台运营访问学校明细需要授权。
- AI 只能使用当前用户有权访问的数据。

### 10.3 生命周期

- 转班：历史归属保留，新任务按新班级产生。
- 转学、休学和毕业：停止新增教学访问，历史按规则归档。
- 教师离职：立即撤销访问。
- 学期结束：正式成绩冻结，修改走修正流程。
- 作业图片、AI 中间数据和正式成绩可配置不同保留周期。
- 删除、匿名化、导出和恢复进入审计记录。
- 学校学生数据不用于训练公共模型，除非存在单独、明确、可撤回授权。

## 11. 原型范围

### 11.1 原型目标

首轮 HTML 原型的目标是验证学校上下文、三种身份和主教学闭环是否能够被理解并连续操作。原型不是 26 个页面的静态目录，也不承担技术可行性验证。

### 11.2 高保真关键场景

原型重点实现以下 14 个可交互场景：

1. 学校选择
2. 身份选择
3. 教师工作台
4. 创建全科作业
5. 学生提交进度
6. AI 批改复核
7. 成绩发布确认
8. 成绩册与学生学情
9. 学生 App 今日学习
10. 在线答题与拍照提交
11. 批改反馈与错题订正
12. 个性化提升与学科教师协同
13. 教务工作台与排课冲突
14. AI 指令中心与连续任务预览

### 11.3 产品结构表达

教师、学生和教务端保留完整一级导航。题库、学生列表、学校组织、教学任务、消息中心和课表结果等页面使用可点击的代表性状态表达，不要求每个二级功能都形成独立高保真流程。

### 11.4 原型验收主线

```text
选择学校和教师身份
→ 创建作业
→ 切换学生身份并提交
→ 切回教师复核与发布
→ 学生查看反馈并订正
→ 教师生成提升计划
→ 班主任查看全科协同
→ AI 指令中心继续生成操作草稿
```

### 11.5 原型演示数据

- 虚构学校：石家庄明德实验中学
- 当前学期：2026—2027 学年第一学期
- 核心班级：七年级一班
- 学生人数：40 人左右
- 演示身份：数学教师兼班主任、任课教师、学生、教务、学校管理员
- 所有姓名、联系方式和成绩均为虚构演示数据

## 12. 视觉与交互原则

- 整体采用专业、克制的教育管理风格。
- 教师和教务端强调任务、表格、状态和高效批量操作。
- 学生 App 使用清晰任务优先级、较大触控区域和适量激励。
- AI 使用统一标识，不以大面积渐变和装饰取代业务信息。
- 风险状态使用图标、文字和颜色共同表达。
- 学校可配置校徽和辅助色，但不改变关键交互。
- AI 面板展开后不得遮挡关键业务数据。
- 高风险操作必须展示结构化影响预览。

## 13. 非功能产品要求

### 13.1 可用性

- 长时间任务显示当前阶段、可离开提示和结果通知。
- 学生答题和拍照上传支持弱网恢复。
- 批量导入必须先校验和预览。
- 重要页面提供明确的空状态和下一步入口。

### 13.2 安全与合规

- 学校间数据严格隔离。
- 角色和数据范围同时校验。
- 敏感导出、成绩发布、调课和删除操作需要确认。
- 学生实名、成绩、作业图片和监护人信息按未成年人敏感数据管理。
- 操作日志应支持按学校、用户、对象和时间查询。

### 13.3 兼容性

- 教师、教务和管理端支持主流桌面浏览器。
- 学生端产品形态同时覆盖 Android 和 iOS。
- 移动端和 Web 使用一致的数据状态和业务口径，但交互分别设计。

## 14. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| AI 主观题判断不稳定 | 成绩可信度下降 | 教师复核、评分点、置信状态和抽样检查 |
| 拍照质量差 | 无法进入批改 | 拍摄质检、缺页检查和断点续传 |
| 多学科任务叠加 | 学生负担过重 | 总任务量控制与班主任协调 |
| 权限配置复杂 | 数据越权 | 角色、学校、班级和学科四层校验 |
| 学校基础数据质量差 | 排课和成绩关系错误 | 导入校验、预览和错误明细 |
| 过度依赖排名 | 学生压力和错误评价 | 学生端弱化排名，突出趋势和知识证据 |
| AI 指令误操作 | 批量影响教学数据 | 草稿、预览、二次确认和审计 |
| 产品范围过大 | 试点难以验证 | 试点优先作业到提升闭环，复杂能力分阶段开放 |

### 14.1 试点假设

- 试点学校指定一名校级负责人和各试点学科教师参与规则确认。
- 学校能够提供七年级三个班的虚构或脱敏基础数据用于原型和试运行。
- 教师愿意为试点作业提供标准答案或评分点，而不是要求 AI 无规则自由评分。
- 学生具备完成 App 作业所需的家庭或学校设备条件。
- AI 不可用时，教师人工流程仍可完成，不形成业务中断。

### 14.2 上线前置依赖

- 学校确认成员、班级、任课关系和数据使用范围。
- 学科负责人确认试点题型的评分规则和人工复核边界。
- 未成年人数据处理、家长报告分享和第三方 AI 数据传输经过专项合规评审。
- 试点前建立教师培训、问题反馈和异常作业人工处理机制。

### 14.3 端到端验收场景

- [ ] 教师能在一个会话内创建包含在线题和拍照题的作业草稿并发布。
- [ ] 学生能完成在线答题、拍照质检、提交和提交状态确认。
- [ ] 系统能区分自动判分、教师复核和无法判断的题目。
- [ ] 教师能在 AI 不可用的情况下继续人工批改并发布。
- [ ] 学生只能在发布后查看成绩、反馈和订正入口。
- [ ] 订正结果能进入知识点证据，并形成教师可确认的提升计划草稿。
- [ ] 任课教师能查看本学科提升点，班主任能查看本班全科任务总量。
- [ ] AI 指令中心能完成查询和草稿生成，但发布成绩等高风险操作必须确认。
- [ ] 切换学校或身份后，页面数据和 AI 上下文同步隔离。

## 16. 术语表

| 术语 | 定义 |
|---|---|
| 学校空间 | 一所学校在平台中的独立租户和数据边界 |
